# IT23183186 Component Guide

Use this guide for the `IT23183186_` screens and services. Use `../Frontend_skill.md` for the shared palette, typography, and widget conventions. Where its general bottom-navigation example conflicts with this guide, follow the navigation rule below for this component.

## Component goal

Build a mobile-friendly decision-support component for Sri Lankan beekeepers. It should combine external weather, available in-hive sensor data, and user-uploaded bee or hive images to explain environmental conditions and show a potential colony-health or disease-risk level.

Treat the proposal as the source for intended requirements, not evidence that a feature or model is already implemented. Do not claim model accuracy, disease diagnosis, live sensor data, or validated treatment advice without evidence.

## User navigation requirement

- The app's **Environment** bottom-bar item opens `IT23183186_environment_dashboard_screen.dart`.
- The Environment dashboard is the entry point for this component's other `IT23183186_` screens.
- Keep the shared bottom bar off the `IT23183186_` pages. The user's current preference is a dashboard-centered flow, not a repeated bottom bar on every component page.
- Make component pages reachable from dashboard actions or from another component page's clear action. Keep back navigation working.
- Do not change other group members' bottom-bar destinations unless asked.

## Inputs and ownership

1. **External weather:** retrieve temperature, humidity, rainfall/precipitation, location, and observation time from the configured WeatherAPI service. Use the apiary GPS/location when available; allow a user-entered location as a fallback. Label this as outdoor weather, not a hive measurement.
2. **In-hive measurements:** integrate the agreed IoT component/API when its data contract is available. The IoT hardware and sensor implementation belong to the teammate responsible for that component. Show missing or stale readings as unavailable; never substitute weather values or invented sample values as live hive readings.
3. **Bee/hive images:** allow capture or gallery upload, preview selected images, validate supported formats and count, and provide an understandable inference state. Use local images only for preview unless a configured model/API is ready.
4. **Audio/acoustics:** this component may display a clear integration state, but acoustic capture/classification belongs to the acoustic component unless responsibility is explicitly reassigned.

## Risk and inference behavior

- The proposal calls for image indicators such as Varroa-related signs and brood disease, then Low/Medium/High risk levels and relevant alerts or recommendations.
- Only name a disease when a trained, tested classifier actually supports that label. A broad class such as `Disease Signs` is not a disease identification.
- When no trained model is bundled or available, allow image selection/preview but report inference as unavailable. Do not fabricate a score or findings.
- A rules-based baseline may combine only real, available evidence and must disclose its rules, inputs, thresholds, and missing inputs. Mark it as preliminary and unvalidated. Do not present a score as a calibrated probability or veterinary diagnosis.
- Keep uncertainty visible. A high-risk result should explain the evidence and recommend human inspection or expert advice rather than prescribe treatment unsupported by validated sources.
- Preserve provenance: show whether each input came from WeatherAPI, the IoT API, or image inference, with location/time where available.

## Implementation plan

Work incrementally and keep each step runnable:

1. **Confirm contracts:** document the WeatherAPI response fields and obtain the IoT teammate's endpoint, payload, hive identifier, timestamps, units, and authentication requirements.
2. **Make the dashboard reliable:** fetch weather by apiary location, show loading/error/stale states, and keep outdoor conditions distinct from in-hive readings.
3. **Prepare image data/model:** identify licensed public datasets and consented local images; record labels and provenance; clean duplicates/corrupt images; preprocess to the model's required input; split train/validation/test without leakage. The proposal targets at least 2,000 labeled images, but this is a research target, not a claim about the current repository.
4. **Connect inference:** verify the model file, label mapping, preprocessing, and output contract before enabling predictions. Keep a clear unavailable state until the model or supported inference API exists.
5. **Build a transparent baseline:** combine image-classifier output with environmental and sensor evidence only after inputs and thresholds are defined. Compare image-only, environmental/IoT-only, and combined approaches.
6. **Add risk history, alerts, and recommendations:** persist the input provenance and result through the agreed backend; make alert rules understandable and prevent duplicate/noisy alerts.
7. **Evaluate and refine:** record accuracy, precision, recall, F1, confusion matrix, and ROC-AUC where suitable. Prioritize recall for disease-risk classes. Evaluate latency, risk agreement with experts, and usability with beekeepers.

## Proposal targets and interpretation

- The proposal's objective mentions **85% accuracy**; treat it as a target to evaluate, not an achieved result. Report actual test-set metrics and class balance.
- The proposal gives different latency figures: **10 seconds** in the evaluation table and **20 seconds** in the non-functional requirements. Confirm the final target with the supervisor; until then, report measured latency and do not claim either target is met.
- The proposal suggests **SUS ≥ 70** for usability if SUS is used. It also calls for expert/beekeeper validation and comparison against baseline models.
- Compare weather-only, image-only, environmental plus IoT, and multimodal approaches where data availability supports the comparison. Do not imply multimodal benefit without measured results.

## Safety, privacy, and reliability

- Describe outputs as **potential risk indicators** and **decision support**, not a confirmed diagnosis.
- Handle API/model failures without crashing. Keep useful UI states when offline or when one data source is missing.
- Protect authenticated user, apiary, and image data; do not log tokens, API keys, or private image contents.
- Collect local images and stakeholder feedback only with appropriate consent. Verify dataset licenses and cite original sources in research reporting.
- Keep recommendations simple, traceable to evidence, and reviewed by appropriate bee-health experts before presenting them as authoritative.
